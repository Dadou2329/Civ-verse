# How to create a civilization

This guide takes a new civilization pack from nothing to a playable, validated pack. It is written
for a developer or an AI coding session working in this repository. The file format is specified
in [docs/PACK_FORMAT.md](docs/PACK_FORMAT.md); writing mechanics is covered in
[HOW_TO_ADD_A_NEW_MECHANIC.md](HOW_TO_ADD_A_NEW_MECHANIC.md). For more depth on single topics:
[docs/STORY_AUTHORING.md](docs/STORY_AUTHORING.md) (dialogues, quests, rules, cinematics),
[docs/EDITOR_GUIDE.md](docs/EDITOR_GUIDE.md) (Civilization Studio),
[docs/MECHANICS_SDK.md](docs/MECHANICS_SDK.md) (code API).

The two playable packs serve as running examples. They run on the same engine and share no
gameplay rule:

| | Door — `civilizations/door` | Memory — `civilizations/memory` |
| --- | --- | --- |
| Title | « La Porte qui n’existe pas » | « Le Nom qu’on t’a volé » |
| Scenario spec | `docs/narrative/DOOR_CIVILIZATION_SCENARIO.txt` | `docs/narrative/MEMORY_CIVILIZATION_SCENARIO.txt` |
| Central rule | an access rank checked by every lock (variable `door.rank`, mechanic `door.access`) | memory shards placed in three slots change what the player perceives (mechanic `memory.chamber`) |
| Scenes | `verrou` (96 × 64 × 120), `porte_absente` (40 × 34 × 64) | `reminence` (96 × 40 × 96), `chambre_blanche` (32 × 24 × 32) |
| Closed doors | component `door.lock`: variants rank, item, condition, sealed, palm, impossible | component `memory.closed`: no rank, a personal refusal |
| Way into the second scene | walk-in `core.portal` (`passage_efface`) | `core.portal` on a lamp, available only while the shard `vente` is anchored and the quest is at stage `chambre` |
| Puzzle | three dials (`door.keyImprint`), solution in `content/rules.json` | three objects on pedestals (`memory.offering`), solution in `content/rules.json` |
| HUD | `door.rankPlaque`, `door.accessDenied` | `memory.chamberHud`, `memory.echoOverlay`, `memory.touch` |
| Panels | `door.imprint`, `door.permissions` (key R) | `memory.chamber` (key C), `memory.offering` |
| Rendering extension | visual `door.spinnerVisual` (`view/spinner.ts`) | view effect `memory.echoEffect` (`view/echoes.ts`) |
| Multiverse | fragment `threshold`, flag `door.finalChoice` | fragment `remanence` (the restoration outcome stays a local variable); reads whether Door is completed |
| Theme | accent `#e3b84d`, titles in Cinzel, cover motif `door` | accent `#f0a040`, titles in Cormorant Garamond, cover motif `memory` |

Throughout the guide, `<id>` is the id of your new pack (for example `ambre`).

---

## 0. Prerequisites and commands

Node.js ≥ 22.12 (`engines` in `package.json`) and `npm install`.

| Command | Purpose |
| --- | --- |
| `npm run dev` | Vite dev server (`127.0.0.1:5173` by default): the game at `/`, Civilization Studio at `/studio.html` |
| `npm run civ -- new-pack <id> --name "Nom affiché"` | create the skeleton of a pack (`tools/cli/newPack.ts`) |
| `npm run civ -- seed <id> [--force]` | write the files generated by `civilizations/<id>/seed/index.ts` |
| `npm run validate` / `npm run civ -- validate <id>` | validate every civilization / only the given ones |
| `npm run test` | Vitest: the `*.test.ts` files of `src/`, `civilizations/`, `tests/unit/`, `tests/acceptance/` and `tools/` (`vitest.config.ts`) |
| `npm run typecheck`, `npm run lint` | TypeScript (strict) and ESLint |
| `npm run check` | `typecheck` + `lint` + `validate` + `test` |

The steps are listed in a logical order, not a mandatory one: content that references a component,
action or condition only validates once the code defining it exists (step 11), so write mechanics
whenever the content needs them.

---

## 1. Design the civilization

1. **Write a scenario spec** in `docs/narrative/<NAME>_CIVILIZATION_SCENARIO.txt`, in French, like
   the two existing ones. Both use the same sections: STATUT ET PÉRIMÈTRE, 1. PROMESSE ET THÈME,
   2. RÈGLES DU MONDE, 3. CARTE ET DIRECTION ARTISTIQUE, 4. PERSONNAGES, 5. MÉCANIQUES ORIGINALES À
   CODER, 6. STRUCTURE NARRATIVE JOUABLE, 7. quests and technical states, 8. CINÉMATIQUES
   MINIMALES, 9. UX ET TEXTE FRANÇAIS, 10. CRITÈRES D'ACCEPTATION, then freedoms and prohibitions
   (Memory adds 11. ARTICULATION ENTRE LES DEUX MINI-CIVILISATIONS).
2. **Fix the stable technical ids in the spec** (its section 7): quest ids, story variables,
   fragment id. The packs use them verbatim: `DOOR_Q00_REVEIL` ... `DOOR_Q04_PORTE_ABSENTE`,
   `door.rank`, `door.varenTrust`, `door.finalChoice`; `MEM_Q00_EVEIL` ... `MEM_Q04_SUJET_ZERO`,
   `memory.leaConsent`, `memory.restorationOutcome`, `global.fragments.remanence`.
3. **Make the rules genuinely different.** The engine imposes no progression model: `core.door`
   has no access rules (comment in `src/engine/core/behaviors/doors.ts`), so each civilization
   brings its own. Door gates its city with ranks (`door.lock` checks `door.rank`). The Memory spec
   forbids reusing that ("Ne pas reprendre la progression par portes et niveaux d'accès"; "Le pack
   n'utilise aucun système de rang comme mécanique centrale"), so its closed doors
   (`memory.closed`) never mention a rank, and its progression comes from shards that change NPC
   recognition (`memory.recognition`), what a place shows (`memory.recollection`) and echoes
   (`memory.echoPoint`). List, for your civilization: the central rule, what the player does that
   they do in no other pack, the HUD that makes that rule visible, the puzzle(s), the endings, the
   multiverse fragment.
4. **Write acceptance criteria** (spec section 10). They become the assertions of your playthrough
   test (step 14). `docs/narrative/TRACEABILITY.md` maps each requirement of the two existing specs
   to its implementation and test; keep the same kind of mapping for yours.

---

## 2. Choose an id and scaffold the pack

1. **Choose the id** carefully: it must match `^[a-z][a-z0-9-]*$`, it is the directory name, the
   namespace of every story variable (`<id>.*`), the prefix of every localization key and of every
   definition id, and the key of saves. `core` is taken; `engine`, `global` and `ui` are reserved
   and refused by the manifest schema. Do not use a prefix of engine events either, such as
   `scene`, `quest`, `item` (list in
   [PACK_FORMAT.md section 7](docs/PACK_FORMAT.md#7-identifiers-and-naming-conventions)).
2. **Run the scaffold:**

   ```sh
   npm run civ -- new-pack <id> --name "Nom affiché"
   ```

   It refuses an existing directory (`Le dossier civilizations/<id> existe déjà : rien n’a été
   modifié.`) and otherwise creates:

   | File | Content |
   | --- | --- |
   | `manifest.json` | `kind: "civilization"`, `name`/`description`/`tagline` keys, `packVersion: "0.1.0"`, `engineApi: "^1.0.0"` (from `ENGINE_API_VERSION`), `dependencies: ["core"]`, `entry: { scene: "depart", spawn: "depart_joueur" }`, `scenes: ["depart"]`, `theme: { accent: "#7fb7d9" }`, `cover: { colors: ["#1c2633", "#3f5d78"], motif: "default" }`, `order: 100` |
   | `pack.ts` | `definePack` with the glob `['./mechanics/**/*.ts', './assets/**/*.ts', './ui/**/*.tsx', './view/**/*.ts', '!./**/*.test.ts']` |
   | `locales/fr-FR.json` | `<id>.name` (the `--name` value), `<id>.description`, `<id>.tagline`, `<id>.scene.depart` |
   | `content/scenes/depart.scene.json` | a 32 × 24 × 32 scene: `core:stone` up to y = 6, a `core:grass` layer at y = 7, a `core.spawn` entity `depart_joueur` at `[16.5, 8, 16.5]` |
   | `mechanics/.gitkeep` | empty |

   Write the `--name` value with French typography (typographic apostrophe `’`): it goes into the
   French table, which `tests/acceptance/localization.test.ts` checks (step 12).
3. **Start (or restart) `npm run dev`.** The card appears in « Civilisations » on the game's main
   menu; the Studio lists the pack in its « Pack » selector (`/studio.html?pack=<id>` opens it
   directly).
4. **Check `pack.ts`**: its glob covers `mechanics/`, `assets/`, `ui/` and `view/`, as in
   `civilizations/door/pack.ts` and `civilizations/memory/pack.ts`. Only files matched by the glob
   are loaded, and only `.tsx` files are matched in `ui/`; add an entry if you create another code
   folder.
5. **Create the content files the Studio cannot create** (its Explorer only creates scenes,
   dialogues, quests, cinematics, logic files and scripts):

   ```json
   { "format": "civverse.items", "version": 1, "items": [] }
   ```
   ```json
   { "format": "civverse.characters", "version": 1, "characters": [] }
   ```
   ```json
   { "format": "civverse.rules", "version": 1, "settings": {} }
   ```

   as `content/items.json`, `content/characters.json` and `content/rules.json` (the last one only if
   a mechanic declares `settings`).
6. **Validate the skeleton** (`npm run civ -- validate <id>`) so that every later error is yours.
   The scaffold provides what validation requires: French keys for the name, description, tagline
   and scene name, an entry scene and an entry spawn.

## 3. Manifest: identity, theme, HUD, cover

Edit `manifest.json` directly or in the Studio (Explorer group « Civilisation et interface »,
`src/studio/editors/ManifestEditor.tsx`, which shows a live HUD preview). Field reference:
[PACK_FORMAT.md section 3](docs/PACK_FORMAT.md#3-manifestjson).

1. **Identity.** Keep the keys `<id>.name`, `<id>.description`, `<id>.tagline` and write their
   French texts in `locales/fr-FR.json`. They are read before the pack loads, for the selection
   card.
2. **Entry point and scenes.** `entry.scene` and `entry.spawn` name the first scene and an entity
   of that scene (Door: `verrou` / `spawn_cell`; Memory: `reminence` / `spawn_banc`). Every scene
   file should be listed in `scenes` (the Studio adds new scenes itself; seeds do not touch the
   manifest).
3. **Theme.** Set `accent` and, optionally, `accentSoft`, `panel`, `panelBorder`, `text`,
   `textDim`, `font`, `titleFont`. They become the CSS variables `--civ-*` used by the game UI and
   by your own HUD CSS. Only fonts bundled by `src/game/main.tsx` load: Alegreya Sans, Cinzel,
   Cormorant Garamond, IM Fell English, JetBrains Mono. Door: amber accent `#e3b84d` and Cinzel;
   Memory: `#f0a040`, a violet `accentSoft` `#c8a8f0` and Cormorant Garamond.
4. **Cover.** `cover.colors[0]` and `cover.colors[1]` make the card gradient. `cover.motif` adds
   the class `cv-motif--<motif>`, styled only for `door`, `memory` and `default` (the scaffold
   value: a horizon of blocks lit with the accent color) in `src/game/styles/game.css`; any other
   value draws no motif. A new motif requires a CSS rule in that engine file.
5. **HUD.** `hud.hide` hides built-in elements (`crosshair`, `prompt`, `objectives`, which also
   hides the on-screen objective markers, `notifications`, `inventory`, `abilities`, `location`).
   Door and Memory hide none and add their own elements with `defineHud` (step 11).
6. **Order and dependencies.** `order` places the card (Door 10, Memory 20, scaffold 100). Keep
   `"dependencies": ["core"]` to use the shared blocks, models, sounds and characters.
7. **Versions.** Leave `packVersion` at `0.1.0`, `engineApi` at `^1.0.0` and `stateVersion` at `1`
   for a first version.
8. `globalWrites` and `fragments` are set in step 13.

## 4. Blocks, models, sounds and music

Asset definitions are TypeScript modules; any exported `define*` value (or array of them) found by
the `pack.ts` glob is registered. Door and Memory keep them in `assets/blocks.ts`,
`assets/models.ts` and `assets/sounds.ts`. Details:
[PACK_FORMAT.md section 5](docs/PACK_FORMAT.md#5-assets-defined-in-code).

1. **Reuse `core` first**: `core:stone`, `core:grass`, `core:cobble`, `core:planks_oak`, roofs,
   glass... (`civilizations/core/mechanics/blocks.ts`), models such as `core:door_wood`,
   `core:barrel`, `core:lantern` (`civilizations/core/models/*.ts`), sounds such as
   `core:door_open`, `core:amb_wind` (`civilizations/core/mechanics/sounds.ts`).
2. **Define what makes the place recognizable.** Door's palette is damp stone, warm brick and pale
   archive stone (`door:damp_stone`, `door:warm_brick`, `door:archive_stone`, the starry
   `door:void`); Memory's is petrol blue, mauve and amber (`memory:black_stone`,
   `memory:petrol_plaster`, `memory:mauve_wood`, `memory:white` for the mental room).
3. **Conventions.** Ids `<id>:<name>`; French `label` and `category` (they are what the Studio
   palette shows: `'Verrou — Faubourg'`, `'Réminence'`). Block textures use the generators of
   `src/engine/core/voxel/textures/generators.ts`; an unknown generator name renders a magenta
   checker and is not reported by validation. Models are drawn with the `ModelBuilder` in
   micro-voxels of 1/16 m. Sounds and music are synthesis recipes: the format has no audio files.
4. Edit these modules in your editor or in the Studio's script editor (Explorer « Scripts »;
   `assets/` and `models/` are writable through the dev API). Under `npm run dev`, a changed pack
   script is re-imported by the Studio without reloading the page (`civ:code-changed` in
   `tools/vite/civDevPlugin.ts` and `src/studio/main.tsx`).
5. `tests/unit/corePack.test.ts` shows how to check that every block has a known texture generator
   and every model builds; you can copy it into your pack's tests.

## 5. Build the world

A scene is a voxel grid plus entities ([PACK_FORMAT.md section 6.1](docs/PACK_FORMAT.md#61-scenes--contentscenesidscenejson)).
There are two ways to produce it, and the packs combine them.

### 5a. Seed script with the build kit

Door and Memory generated their scenes and cinematics with seed scripts; their main scenes were
then edited in the Studio (see the `editor.notes` quoted below). Dialogues, quests, logic, items,
characters and rules were not generated: their seeds return scenes and cinematics only.

`seed/index.ts` exports `seed()`, which returns `{ "<path relative to the pack>": document }`.
`civilizations/door/seed/index.ts`:

```ts
import { buildVerrou } from './verrou.ts';
import { buildAbsente } from './absente.ts';
import { buildCinematics } from './cinematics.ts';

export function seed(): Record<string, unknown> {
  const files: Record<string, unknown> = {
    'content/scenes/verrou.scene.json': buildVerrou(),
    'content/scenes/porte_absente.scene.json': buildAbsente(),
  };
  for (const c of buildCinematics()) files[`content/cinematics/${c.id}.cinematic.json`] = c;
  return files;
}
```

The kit is `@sdk/build` (`src/sdk/build.ts`, `src/sdk/buildKit.ts`):

- `new SceneBuilder(id, nameKey, size, environment)`; `b.volume` is a `VoxelVolume`;
  `b.entity(id, position, components, { yaw, name, folder, tags, scale })` refuses duplicate ids;
  `b.inFolder(folder, fn)` groups entities in the Studio hierarchy; `b.build(editor?)` returns the
  scene document.
- Voxel helpers from `src/engine/core/voxel/construct.ts`: `fillBox`, `clearBox`, `walls`,
  `hollowBox`, `stairs`, `gableRoof`, `pyramidRoof`, `cylinder`, `cone`, `sphere`, `arch`,
  `opening`, `scatter`, `copyRegion`/`pasteRegion`...
- Kit helpers: `house` (walls, windows, door openings, roof), `doorSpot` (door entity position and
  yaw for an opening), `railing`, and entity shortcuts `model`, `deco`, `light`, `sign`, `zone`,
  `npc`.

From `civilizations/door/seed/verrou.ts`:

```ts
export function buildVerrou(): SceneDoc {
  const s = new SceneBuilder('verrou', 'door.scene.verrou', SIZE, VERROU_ENV);
  terrain(s);
  s.inFolder('Faubourg Bas', () => faubourg(s));
  s.inFolder('Galerie des Métiers', () => galerie(s));
  s.inFolder('Archives du Haut', () => archives(s));
  return s.build({ camera: { position: [48, 30, 6], target: [48, 12, 40] }, notes: 'Généré par civilizations/door/seed/verrou.ts puis édité dans le Studio.' });
}
```

Both packs keep coordinates in a layout module shared by the scene seeds and the cinematic seeds
(`civilizations/door/seed/layout.ts` with the tiers `G0 = 8`, `G1 = 20`, `G2 = 32`;
`civilizations/memory/seed/layout.ts` with the ground at `G = 6`), so that cameras frame the right
places. Both define `at(x, y, z) = [x + 0.5, y, z + 0.5]`: the center of a cell column at a walking
height.

Seed scripts run in Node through `tsx` (no Vite, no `import.meta.glob`), import `@sdk/build` and
sibling files with their `.ts` extension, are type-checked by `tsconfig.node.json` (they are
excluded from `tsconfig.json`), and are never loaded by the game.

Run:

```sh
npm run civ -- seed <id>
```

Scenes, cinematics, dialogues, quests, logic files and prefabs returned by the seed are checked
against their schema (other files are written unchecked); each file is written as
`✓ <path> (N Ko)`; an existing file is kept
(`· <path> existe déjà (conservé ; --force pour régénérer)`); an invalid file is not written and
the command exits with code 1. Block ids are not checked at this stage: run the validation
afterwards.

**The rule: the seed generates the first version; afterwards the JSON file is canonical.**
`src/sdk/build.ts` states it ("A seed generates the first version of a scene; afterwards the JSON
file is the source of truth and is edited in Civilization Studio"), and so do the comments of both
`seed/index.ts`. `--force` rewrites every file the seed returns, with no merge: a file whose content
would not change is left alone (`· <path> inchangé`), any other existing file is first copied to
`.civ-backups/civilizations/<id>/<path>.<timestamp>.seed.bak` (the CLI prints
`ancienne version conservée : <backup path>`).
Use `--force` only while nobody has edited the generated files, by hand or in the Studio. Once they
have been edited, change them in the Studio or by hand, not by re-seeding. Door's `verrou` and
Memory's `reminence` and `chambre_blanche` record in `editor.notes` that they were edited in the
Studio after generation (`"Généré par civilizations/door/seed/verrou.ts puis édité dans le
Studio."`): never run `seed door --force` or `seed memory --force`. To regenerate a single file of
your own pack that has no manual edits, delete it and run the seed without `--force`: files that
exist are kept, missing ones are written.

### 5b. Civilization Studio

Open `/studio.html?pack=<id>` under `npm run dev`.

- Explorer « Scènes » ＋: identifier, place name (in French; the Studio creates the key
  `<id>.scene.<scene>`), size from 8 to 256 blocks per axis (default 64 × 32 × 64). The new scene
  has a dirt ground topped with grass, a default spawn entity `depart`, the environment of the open
  scene (or a default one), and its id is added to `manifest.scenes`.
- Viewport: block tools (place, erase, paint, box, pick) with the block picker, a select tool with
  move/rotate/scale gizmos, « ＋ Ajouter » for entity templates (`src/studio/core/templates.ts`:
  Personnage, Porte, Décor (modèle), Lumière, Panneau, Particules, Source sonore, Objet à ramasser,
  Document à lire, Point d’interaction, Déclencheur, Zone nommée, Repère, Point d’apparition,
  Passage vers une scène), « Préfabriqués » to capture a region of the scene and paste it
  elsewhere.
- Entity templates create their texts as keys of `locales/fr-FR.json`. In the inspector and the
  editors, a text field edits the French text of its key; « ＋ Écrire un texte » creates a new
  `<id>.` key, and a key of another table (such as `core.prompt.examine`) can be copied into the
  pack to be changed (`TextField` in `src/studio/fields/PropField.tsx`).
- Nothing is written until « 💾 Enregistrer » (Ctrl+S). Each save replaces the file atomically and
  copies the previous version to `.civ-backups/` (ignored by git).

## 6. Characters, NPCs and other entities

Entity reference: [PACK_FORMAT.md section 6.1](docs/PACK_FORMAT.md#61-scenes--contentscenesidscenejson).

1. **Appearances** go in `content/characters.json` (Studio group « Personnages », with a 3D
   preview): body, height, skin, eyes, hair, face, outfit, accessories, idle mood, voice pitch. Ids
   are `<id>:<name>` (`door:mira`, `memory:oriane`); the name is a key (`door.npc.mira`). The `core`
   appearances (`core:citizen_a` ... `core:citizen_d`, `core:child`, `core:guard`) are available
   too.
2. **NPCs** are entities with `core.npc`: `character`, `name` (key), `dialogue`, `mode` (`static`,
   `wander`, `patrol` with `patrol` markers, `follow`), `barks` (keys) and `barkInterval`,
   `lookAtPlayer`, `speed`... Door's NPCs are plain `core.npc` entities:

   ```json
   { "id": "mira", "position": [77.5, 8, 22.5],
     "components": { "core.npc": { "character": "door:mira", "name": "door.npc.mira", "dialogue": "mira",
       "barks": ["door.bark.mira.1", "door.bark.mira.2"], "barkInterval": 30 } },
     "rotation": [0, 270, 0], "folder": "Faubourg Bas" }
   ```

   Memory composes extra components on its NPCs: `memory.recognition` (levels chosen by
   conditions, each with its own barks) on `lea`, `oriane` or `aurele`, and `memory.echoPoint` on
   `silas`. Your mechanics can do the same: an NPC's behavior is the sum of its components.
3. **Spawn points**: `core.spawn` entities (`isDefault: true` for the scene's default). The
   manifest `entry.spawn` and the portals name them.
4. **Scene changes**: `core.portal` (`scene`, `spawn`, `mode` `interact` or `walk`, `condition`,
   `unavailable` text) or the action `core.changeScene`. Door walks into the erased corridor:

   ```json
   { "id": "passage_efface", "position": [42.5, 24, 104.5],
     "components": { "core.portal": { "scene": "porte_absente", "spawn": "spawn_arrivee", "mode": "walk",
       "size": [1.6, 2.4, 2.6], "prompt": "door.prompt.descend" } },
     "folder": "Archives du Haut" }
   ```

   Memory's white room is reached through a lamp that only works with the right shard anchored
   (`lampe_resonance` in `reminence.scene.json`: `"mode": "interact"` and a `condition` combining
   `memory.anchored` with `core.questStage`). Spawn ids in portals are plain strings: validation
   does not check them; a wrong id logs `Point d’apparition introuvable` at runtime and the scene's
   default spawn is used.
5. **Doors**: `core.door` (model, name key, size, hinge, sounds, auto-close) plus your own lock
   component if passage is ruled by your mechanics (Door: `door.lock`; Memory: `memory.closed`).
6. **Interactions and story-driven world**: `core.interactable` (actions on E or F),
   `core.pickup` (gives an item), `core.readable` (shows a document, then runs actions),
   `core.trigger` (actions on entering a volume), `core.zone` (named places, music and ambience),
   `core.conditional` (show, hide, enable or move an entity according to conditions), `core.light`,
   `core.sign`, `core.particles`, `core.sound`, `core.model`, `core.marker`.
7. **Coordinates**: positions are in meters on the voxel grid, `y` is the walking surface (Door's
   lower city stands on `y = 8`), and rotations are `[0, yaw, 0]` in degrees. Entity ids must be
   unique in their scene; dialogues, quests, cinematics and logic refer to them by id.

## 7. Dialogues

Files `content/dialogues/<dialogue>.dialogue.json`; Studio: Explorer « Dialogues » ＋ (graph
editor). Format: [PACK_FORMAT.md section 6.2](docs/PACK_FORMAT.md#62-dialogues--contentdialoguesiddialoguejson).

1. Attach a dialogue to an NPC with `core.npc.dialogue`, or start it with the action
   `core.startDialogue`.
2. Start with a **routing node** (empty `text`, `branches` tested in order, then `next`) to pick the
   right conversation from the story state. Door's `noe` starts at `route`, whose branches test
   `door.metNoe`, `door.metMira`, quest statuses and `door.rankAtLeast`. Memory's `file` dialogue is
   the smallest complete example:

   ```json
   {
     "format": "civverse.dialogue", "version": 1, "id": "file", "start": "route",
     "speakers": { "vendeur": { "name": "memory.speaker.vendeur" } },
     "nodes": [
       { "id": "route", "text": "",
         "branches": [{ "condition": { "type": "core.var", "var": "memory.illegalCopiesExposed", "op": "==", "value": true }, "next": "after" }],
         "next": "f1" },
       { "id": "f1", "speaker": "vendeur", "text": "memory.dlg.file.f1", "end": true },
       { "id": "after", "speaker": "vendeur", "text": "memory.dlg.file.after", "end": true }
     ]
   }
   ```

3. Put the consequences of a line in its `actions` (run when the node is entered) and the
   consequences of a choice in the choice's `actions`. Door's `noe` node `intro4` gives the rank-0
   plaque and sets the rank (`core.giveItem`, `door.setRank`, `core.setVar`). Memory's `lea`
   dialogue records each person's consent in a variable (`memory.leaConsent`,
   `memory.silasConsent`), and the `memory.restore` action reads the variable it is given:

   ```json
   { "id": "consent_ask2", "speaker": "lea", "text": "memory.dlg.lea.consent_ask2",
     "actions": [{ "type": "core.setVar", "var": "memory.leaConsent", "value": "accepte" }], "next": "key_lea" }
   ```
   ```json
   { "type": "memory.restore", "shard": "vente", "to": "silas", "consent": "memory.silasConsent", "refused": "memory.notify.silasRefuses" }
   ```

4. `speaker` is an entity id of the pack's scenes, `player`, `narrator`, or a key of `speakers`
   (for someone who is not an entity). Choices with a `condition` are hidden when it fails unless
   `showDisabled`; `once` hides a choice after it was picked; `"next": null` ends the dialogue.
5. Mark the last node of each path with `"end": true`, as the packs do. Validation warns about a
   node without text, `next`, branches or choices that ends a dialogue without it.

## 8. Quests

Files `content/quests/<QUEST_ID>.quest.json`; Studio: Explorer « Quêtes » ＋. Format:
[PACK_FORMAT.md section 6.3](docs/PACK_FORMAT.md#63-quests--contentquestsidquestjson).

1. Use the ids of your spec (`DOOR_Q00_REVEIL`, `MEM_Q01_MELODIE`). Keys follow
   `<id>.quest.<QUEST_ID>.title`, `.summary`, `.<stage>`, `.<stage>.<objective>`.
2. Complete objectives in one of three ways: a condition (`completeWhen`, re-evaluated on every
   event), an event (`completeOn`, e.g. Memory's `{ "event": "memory.examined", "where": { "shardId":
   "jardin" } }`), or an explicit `core.completeObjective` action (Door's trigger `trig_cell_exit`
   completes `DOOR_Q00_REVEIL/sortir`). An objective with none of the three gets a validation
   warning.
3. Use `progress` for counters (Memory: `{ "var": "memory.objectsFound", "count": 3 }`),
   `optional` for objectives that must not block the main path, `target` (an entity id) for the
   on-screen marker that the game draws, with the distance, over the target of each open objective
   of the quest shown by the objective tracker, and `targetScene` to draw that marker only in one
   scene (entity ids are local to a scene).
4. Chain quests explicitly. The first quest of each pack is started by the `onComplete` of its
   opening cinematic (`C01_eveil` starts `DOOR_Q00_REVEIL`, `M01_marche` starts `MEM_Q00_EVEIL`),
   and the quests' `onComplete` actions start the following ones (`DOOR_Q00_REVEIL` →
   `DOOR_Q01_EMPREINTE`; `MEM_Q01_MELODIE` ends with a notification then `core.startQuest` of
   `MEM_Q02_REGISTRE`). `autoStart`, `startWhen` and `startOn` are the alternatives; neither pack
   uses them.
5. Stages follow the array order unless `next` says otherwise; `completion: "any"` models
   alternative solutions.

## 9. Logic rules

Files `content/logic/<file>.logic.json`; Studio: Explorer « Logique » ＋ (visual rule editor).
Format: [PACK_FORMAT.md section 6.5](docs/PACK_FORMAT.md#65-logic-rules--contentlogicidlogicjson).

1. A rule is « QUAND événement [filtre] SI condition ALORS actions SINON actions ». Every matching
   enabled rule runs; `once` rules run until their condition passes once (saved with the game);
   `scene` limits a rule to one scene.
2. Start the civilization from a rule on `civ.started`. Door:
   `{ "event": "civ.started" }` → `core.playCinematic` `C01_eveil`. Memory first sets a variable,
   then plays `M01_marche`.
3. Keep one `main` file for the whole civilization and one file per extra scene (Door
   `absente.logic.json`, Memory `blanche.logic.json`, whose rules set `"scene"`).
4. React to your own events: an event documented with `defineEvent` can be used in `when`
   (Door's `preuves_reunies` rule listens to `door.evidenceFound`). Undocumented events get a
   validation warning.

## 10. Cinematics

Files `content/cinematics/<id>.cinematic.json`; Studio: Explorer « Cinématiques » ＋ (timeline
editor with camera preview; a new cinematic starts with a camera key at the editor camera). Format:
[PACK_FORMAT.md section 6.4](docs/PACK_FORMAT.md#64-cinematics--contentcinematicsidcinematicjson).

1. Door and Memory generate their cinematics from the seed layout (`seed/cinematics.ts` in both
   packs) so that cameras frame the right places; the comment at the top of
   `civilizations/door/seed/cinematics.ts` says the JSON files are then edited in the Studio's
   cinematic editor. Door's helper `doc()` in that file sets `skippable`, `letterbox`,
   `lockPlayer`, `hideHud` to `true` and `returnCamera` to `"blend"` for every cinematic.
2. Every cinematic of both packs is skippable (`tests/acceptance/J-regression.test.ts` checks it
   for every bundled civilization). Skipping runs the remaining essential action items and `onComplete`, and
   skips presentational actions (`core.wait`, `core.playSound`, `core.say`...). Put every story
   state change in `onComplete` or in essential `actions` items, never only in timing.
3. Play cinematics with `core.playCinematic` (`wait: true` to continue the action list after it).
   Door's epilogue ends the civilization from its `onComplete` (step 13).

## 11. Mechanics

How to write each kind of definition is the subject of
[HOW_TO_ADD_A_NEW_MECHANIC.md](HOW_TO_ADD_A_NEW_MECHANIC.md). What a civilization needs to know:

1. **Where.** Put definitions under `mechanics/` (logic and rules), `ui/` (`.tsx`, React) and
   `view/` (Babylon.js). Any exported `define*` value is registered; there is no list to update.
   Give each one an id prefixed with your pack id (`<id>.<name>`, `<id>:<name>` for assets): when
   the pack loads, other ids are logged as errors (`Identifiant « … » : « <id>.<nom> » attendu.`),
   which validation lists too (step 15). Import only `@sdk`, `@sdk/ui` and `@sdk/view` (ESLint
   rule for `civilizations/**`).
2. **What.** Door and Memory each implement their spec's section 5:

   | Kind | Door | Memory |
   | --- | --- | --- |
   | `defineMechanic` | `door.access` (rank, refusals, key R), `door.keyImprint` (three dials) | `memory.chamber` (shards and slots, key C), `memory.echoes`, `memory.offering` (depends on `memory.chamber`) |
   | `defineBehavior` | `door.lock`, `door.memory`, `door.restricted`, `door.watcher`, `door.ambientLoop`, `door.spinner` | `memory.device`, `memory.closed`, `memory.echoPoint`, `memory.pedestal`, `memory.recollection`, `memory.recognition` |
   | `defineAction` | `door.setRank`, `door.openImprint`, `door.addEvidence`, `door.foundPoster` | `memory.giveShard`, `memory.anchorShard`, `memory.removeShard`, `memory.examineShard`, `memory.openChamber`, `memory.restore`, `memory.trade`, `memory.playEcho` |
   | `defineCondition` | `door.rankAtLeast`, `door.imprintReady` | `memory.anchored`, `memory.shardState`, `memory.consented` |
   | `defineEvent` | 7 events (`door.rankChanged`, `door.evidenceFound`...) | 15 events (`memory.examined`, `memory.echoPlayed`...) |
   | `defineHud` / `definePanel` | `door.rankPlaque`, `door.accessDenied` / `door.imprint`, `door.permissions` | `memory.chamberHud`, `memory.echoOverlay`, `memory.touch` / `memory.chamber`, `memory.offering` |
   | `defineVisual` / `defineViewEffect` | `door.spinnerVisual` | `memory.echoEffect` |

3. **Data in `content/rules.json`, not in code.** A mechanic's `settings` (declared with `prop.*`)
   are edited in the Studio (« Règles des mécaniques ») and stored in `content/rules.json`. Door
   stores the dial solution (`door.keyImprint`: `dial1`, `dial2`, `dial3`) and the permission-map
   key; Memory stores its shards, echoes, the order of the three-object puzzle and the chamber key.
   Validation checks the text keys, references and nested logic of the declared fields, not
   numbers, other plain values or unknown fields: test what `rules.json` contains (step 14). Code
   that needs a setting reads it with `ctx.settings.of(id)`: Door's permissions panel and Memory's
   chamber panel close on their configured key, and their HUDs display it with `keyLabel` from
   `@sdk/ui`.
4. **State and variables.** Mechanic and component state declared with
   `state: { version, initial }` is saved with the game. Story variables are written with
   `ctx.vars.set('<id>.x', ...)`; writing another namespace throws. `door.access` declares
   `door.rank` with `ctx.vars.declare` so that dialogues, quests and conditions read it like any
   variable.
5. **Studio scaffolding.** Explorer « Scripts » ＋ « Nouveau script » creates
   `mechanics/<nom>.ts` from a typed template (behavior, action, condition or mechanic) with the id
   `<id>.<nom>`; the script editor shows type errors from the project's TypeScript service. The
   dev API writes `manifest.json` and the `.json`, `.ts` and `.tsx` files of `content/`,
   `locales/`, `mechanics/`, `ui/`, `view/`, `assets/` and `models/` (`WRITABLE_PACK_DIRS` in
   `src/engine/platform/devApiRules.ts`); other files, such as `pack.ts`, open read-only
   (« Lecture seule »), and `seed/` and `tests/` are not listed.

## 12. French texts

The whole player-facing game is in French (`docs/narrative/MISE_A_JOUR_PROMPT_FRANCAIS.txt`).
Reference: [PACK_FORMAT.md section 8](docs/PACK_FORMAT.md#8-localization).

1. Player-visible content never holds French text directly: every such field holds a key of
   `locales/fr-FR.json`, and validation reports raw text (`Texte brut au lieu d’une clé de
   traduction`) and missing keys (`Clé de traduction manquante en français`). Editor-only fields,
   which players never see (entity `name` and `folder`, dialogue and cinematic `title`, scene
   `editor.notes`, block and model labels), hold plain French text.
2. Prefix every key with `<id>.`. All tables are merged at runtime, and
   `tests/acceptance/localization.test.ts` fails on a key outside the pack's namespace.
3. Follow the key layout of Door and Memory (`<id>.dlg.<dialogue>.<node>`,
   `<id>.quest.<QUEST>.<stage>.<objective>`, `<id>.cin.<cinematic>.<n>`, `<id>.item.<item>.desc`...).
4. In code, use literal keys: `ctx.t('<id>.notify.x')` in mechanics, `useT()` in React components.
   `npm run validate` checks literal `t('...')` keys. Keys built at runtime
   (`` t(`<id>.rank.${n}`) ``) are not checked by validation; in `ui/**/*.tsx` the localization test
   only requires at least one key under their prefix, elsewhere nothing checks them. Do not write
   literal text in `ui/**/*.tsx` (JSX text or `title`, `placeholder`, `aria-label`, `alt`, `label`
   attributes): the localization test reports it.
5. Write the texts in the Studio (« Textes », or directly in the inspectors) or in the JSON file.
   The localization test also requires French typography and clean values in every table: no empty
   or placeholder value, no leading, trailing or double spaces, typographic apostrophes (`’`, the
   Studio converts `'` as you type), no-break spaces before `? ! ; :` and inside `« »`, none of the
   English words it lists. Read the test for the exact rules.
6. Only `locales/fr-FR.json` is allowed: the localization test fails on any other table in
   `civilizations/*/locales/`.
7. Messages support `{name}` interpolation and ICU plurals/selects
   (`{count, plural, one {# éclat} other {# éclats}}`). A missing key shows `⟦key⟧` in the game;
   in development the F3 overlay lists the missing keys.

## 13. Multiverse fragment and ending

Reference: [PACK_FORMAT.md section 10](docs/PACK_FORMAT.md#10-multiverse-fragments-flags-and-write-permissions).

1. **Declare** the fragment and the global paths you will write:

   ```json
   "globalWrites": ["fragments.threshold", "flags.door.*"],
   "fragments": [{ "id": "threshold", "name": "door.fragment.threshold", "hint": "door.fragment.threshold.hint", "icon": "fragment" }]
   ```

   Memory: `"globalWrites": ["fragments.remanence"]` (its scenario keeps social states local, so it
   writes no global flag), fragment `remanence` with the icon `circle`. Fragment ids are shared by all packs: pick a unique one. The fragment appears
   in the « Registre des éveils » screen.
2. **Grant** it from your story with `core.grantFragment`, and record the outcome that other
   civilizations may read with `core.setGlobalFlag` under your own prefix (Door does; Memory keeps
   its outcome in a local variable). Both packs grant the fragment in a rule triggered when the
   player picks up a local item (`door:fragment_seuil`, `memory:remanence`): the item stays local,
   the fragment is global. A write that `globalWrites`
   does not allow throws at runtime, logs an error and stops the rest of the action list;
   validation does not detect it, the playthrough test does (assert that `logHub.errors()` is
   empty).
3. **End** the civilization: Door's epilogue cinematics end with `core.showEndScreen`, a
   `door.finished` variable, then `core.finishCivilization`, which marks the civilization completed
   in the global state and emits `civ.finished`; the game then saves and returns to the selection
   screen.
4. **Optionally react to other civilizations, read-only and never as a requirement** (Memory spec,
   section 11: each story must be playable first). Memory's white room plays `M04b_vision_seuil`
   instead of `M04b_vision` when `{ "type": "core.civCompleted", "civ": "door" }` holds
   (`content/logic/blanche.logic.json`). Other read access: `core.hasFragment`, `core.globalFlag`,
   variables `global.*`. Local variables of another civilization cannot be read.

## 14. Tests

Vitest runs `civilizations/**/*.test.ts` (`vitest.config.ts`). Write
`civilizations/<id>/tests/<id>.playthrough.test.ts` that plays the story like a player, as
`civilizations/door/tests/door.playthrough.test.ts` and
`civilizations/memory/tests/memory.playthrough.test.ts` do. Their header states the goal: they
"prove that the ending is reachable without dead ends, on each branch".

```ts
import { describe, expect, it } from 'vitest';
import { GlobContentProvider } from '@engine/platform/globContent';
import { advance, advanceDialogue, choose, createHeadlessGame, flush, skipCinematics, talk, walkTo, type HeadlessGame } from '@engine/core/testing/headless';
import { parseSave } from '@engine/core/save/saveFormat';
import type { GameSession } from '@engine/core/sim/session';

async function start(): Promise<HeadlessGame> {
  const game = await createHeadlessGame(new GlobContentProvider());
  await game.session.loadCivilization('door', { fresh: true });
  await advance(game.session, 0.3);
  return game;
}

async function interact(session: GameSession, entityId: string, offerId?: string): Promise<boolean> {
  await walkTo(session, entityId);
  const ok = await session.interaction.interactWith(entityId, 'primary', offerId);
  await flush();
  return ok;
}
```

(Excerpt from the beginning of the Door test.) Tools from
`src/engine/core/testing/headless.ts`:

| Helper | What it does |
| --- | --- |
| `createHeadlessGame(provider)` | a `GameSession` without rendering, with a `HeadlessUi` that records notifications, documents, end screens, open panels, HUDs |
| `advance(session, seconds)` | advances the simulation in fixed steps, letting async logic run |
| `walkTo(session, entityId)` | A* with the player's size (jumps up to 1.2 m, closed doors block); throws `Inaccessible à pied` when there is no path, which is how a dead end in the level is detected |
| `talk(session, entityId, choices)` | walks to the NPC, opens its dialogue and answers with the given choice ids; throws if the dialogue does not end |
| `choose`, `advanceDialogue` | step through a dialogue |
| `skipCinematics(session)` | skips the running cinematic like a player |
| `session.interaction.interactWith(id, 'primary' or 'secondary', offerId?)` | interacts through the game's pipeline, so locks can refuse |

What the two playthroughs assert, and yours should too:

- each branch of the story reaches the end: Door plays « testimony + listen » and « forged report +
  open »; Memory plays the help and trade paths and the refusals;
- quest statuses and stages (`session.quests.status(...)`), variables (`session.vars.get(...)`),
  inventory (`session.civ!.ctx.inventory.has(...)`), mechanic APIs
  (`session.civ!.mechanics.get('door.keyImprint')!.api`);
- the ending: `game.ui.endScreens`, `session.multiverse.progress('<id>').completed`, global flags
  (Door checks `door.finalChoice`; Memory checks that it writes no `memory.*` flag);
- no logged error: `expect(game.session.logHub.errors()).toEqual([])`;
- persistence: `buildSaveGame`, `JSON` round trip, `parseSave`, `applySaveGame` in a new session,
  `loadCivilization('<id>')` without `fresh`, then continue to the end (Door: « the evidence
  persists through a save and a reload »);
- cross-civilization variants: Memory calls `game.session.multiverse.markCompleted('door')` before
  loading Memory to test its Door-aware branch.

Each Door test passes a 120 000 ms timeout and each Memory test 180 000 ms (the default is
30 000 ms in `vitest.config.ts`). Two more patterns are available: validation inside a test
(`tests/acceptance/J-regression.test.ts` calls `validateCivilization` and expects
`report.issues` to be empty, for every bundled civilization — yours included once its manifest
exists), and unit tests of a mechanic on an
in-memory pack with `MemoryContentProvider` (`src/engine/core/sim/session.test.ts`,
`tests/acceptance/G-mechanics-extensibility.test.ts` with its fixture pack
`tests/acceptance/fixtures/lanterne`).

Run one pack's tests with `npx vitest run civilizations/<id>`, everything with `npm run test`.

## 15. Validation

1. `npm run civ -- validate <id>` while working, then `npm run validate` (all civilizations).
   Fix every `erreur`; read every `attention` (undocumented events, objectives that can never
   complete, entities of another scene, empty dialogue nodes). The problems found while loading
   your pack are listed too: content files that fail their schema, definition ids of the wrong
   form, document ids that differ from their file name (`attention`). The exit code is 1 as long as
   one error remains.
2. In the Studio, « ✔ Valider » runs the same checks on the working copies, unsaved edits
   included, and lists them in the « Problèmes » tab.
3. `npm run check` before finishing: types (including seeds), lint (including the import rule for
   pack code), validation and all tests.
4. Validation does not cover everything (list in
   [PACK_FORMAT.md section 12.4](docs/PACK_FORMAT.md#124-not-checked-by-validation)): numbers,
   enums and other plain values of props and of `rules.json` settings, spawn ids of portals,
   fragment and flag names, and global write permissions. The playthrough test covers what
   validation cannot.

## 17. Keep the other civilizations intact

1. Only add or change files under `civilizations/<id>/` (and your spec in `docs/narrative/`). Do
   not edit `civilizations/door`, `civilizations/memory` or `civilizations/core` for your pack:
   changing a `core` block or model changes the Door and Memory worlds too.
2. Prefix every id with your pack id: the pack load logs an error for each definition id of
   another form, and validation lists it (step 11). Blocks, models, items, actions, conditions and
   events that collide with an existing id are refused at registration
   (`... est déjà défini par "<pack>"`, or `... est déjà enregistré(e) par "<pack>"` for actions,
   conditions and events); sounds, music, visuals and view effects silently replace the previous
   one. The Studio keeps only the open pack and its dependencies registered (switching packs
   unloads the others).
3. Write only your variables (`<id>.*`) and the global paths of your `globalWrites`.
4. If the engine really needs a change (a cover motif in `src/game/styles/game.css`, a new
   built-in), keep it additive and run the Door and Memory tests.
5. Shared tests watch every pack: `tests/acceptance/localization.test.ts` checks every table under
   `civilizations/*/locales/`; `tests/acceptance/J-regression.test.ts` expects no manifest issue
   for any pack and full validation of Door and Memory; the Door and Memory playthroughs must keep
   passing. Finish with `npm run validate` (no argument) and `npm run test`.
